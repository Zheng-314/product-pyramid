# Layer 3: 用户需求分析

## 3.1 用户分析：身份、资源、动机

收拢各种角度，聚焦三个核心维度：

| 维度 | 核心问题 | 为什么重要 |
|------|---------|-----------|
| **身份** | 用户是谁？（职业、角色、人生阶段） | 身份决定场景，场景决定需求 |
| **资源** | 用户有什么？（钱、时间、注意力、认知、社交资本） | 资源决定他能用什么、愿意换什么 |
| **动机** | 用户要什么？（深层驱动力） | 动机决定他会不会行动、会不会坚持 |

性别、年龄、付费能力、用户场景等角度，都可以围绕这三点去考虑。

### 用户拥有的5种资源

| 资源 | 核心问题 | 产品意义 |
|------|---------|---------|
| **钱** | 他愿意为这件事花多少钱？ | 定价、商业模式 |
| **时间** | 他愿意为这件事花多少时间？ | 产品深度、使用频率 |
| **认知/技能** | 他懂多少？需要手把手教吗？ | 教育成本、产品复杂度 |
| **注意力** | 他愿意为这件事分出多少脑子？ | 界面复杂度、干扰程度 |
| **社交资本** | 他能影响多少人？愿意分享吗？ | 裂变、口碑传播 |

## 3.2 用户画像

### 为什么要有用户画像

- 统一团队内部对用户的感知和看法
- 作为产品准则，对决策起到"法官"的作用

### 如何运用

- 拉团队开会，明确用户画像确保对"为谁做产品"有统一认知
- 做产品的增删功能都应该考虑到用户画像，看是否合适

### 画像要素

- 姓名、年龄、职业
- 日常行为习惯
- 痛点和需求
- 使用产品的典型场景
- 一句话引言（让画像鲜活起来）

## 3.3 用户场景

### 为什么要有用户场景

- 用户画像告诉你"谁会用"，但用户无法脱离环境存在
- 同一个人，在工位上加班和在地铁上通勤时，对同一个产品的需求、耐心、操作方式完全不同
- 场景决定了用户的使用环境、注意力状态、操作限制、情绪状态
- **没有场景的需求是伪需求**

### 场景四维度

| 维度 | 核心问题 |
|------|---------|
| **时间** | 用户在什么时候用？ |
| **地点** | 用户在什么地方用？ |
| **情绪** | 当时是什么情绪状态？ |
| **行为** | 他在做什么事的时候会想到你的产品？ |

### 如何使用

1. **列出所有场景**：从时间、地点、情绪、行为四个维度穷举
2. **找出核心场景**：最高频、最痛点、最无法替代的场景。判断标准：用户在这个场景下不用你的产品，会感到明显的不便或损失
3. **围绕核心场景设计功能**：砍掉在核心场景下用不到的功能
4. **用场景检验每个决策**：每次加新功能、改交互时，问自己：用户在核心场景下会怎么用？

### 场景分析模板

```
场景描述：[具体描述]
- 时间：[什么时候]
- 地点：[在哪里]
- 情绪：[什么状态]
- 行为：[在做什么]

场景对产品设计的指导：
- [指导1]
- [指导2]

如果没定义这个场景，会发生什么：
- [可能的错误决策]
```

## 3.4 用户故事

### 为什么要有用户故事

- 用户画像是"谁"，用户场景是"在什么情况下"，用户故事把两者串起来，变成团队可执行的具体任务
- 防止功能堆砌：每个功能都必须回答"为谁、什么场景、解决什么问题"
- 统一团队认知：开发、设计、运营都能用同一句话理解要做什么

### 标准格式

> 作为一个[用户画像]，我想要[某个功能]，以便[实现某个价值]。

### 如何使用

1. **写核心故事**：每个产品只应该有 1-3 个核心用户故事，描述最重要的行为路径。如果用户不能完成这个故事，产品对他毫无价值
2. **拆分辅助故事**：围绕核心故事拆出更细粒度的任务，每个辅助故事必须服务于核心故事，否则砍掉
3. **用核心故事定义 MVP**：MVP 的范围就是"核心故事能跑通"的那条线，辅助故事往后排

### MVP 判断原则

- MVP 只包含核心故事 + 必要的辅助故事
- 在核心场景下用不到的功能，即使再好也是噪音
- AI 时代，用户对 MVP 的期待越来越高，但核心原则不变：先跑通核心路径

## 引导问题

1. 你的目标用户是谁？他们的身份、资源、动机分别是什么？
2. 你能不能描述一个具体的用户画像？给他起个名字，描述他的一天。
3. 他最可能在什么场景下使用你的产品？描述那个场景。
4. 他的核心用户故事是什么？如果他只能完成一件事，那件事是什么？
5. MVP 的范围是什么？哪些功能是必须的，哪些可以往后排？
